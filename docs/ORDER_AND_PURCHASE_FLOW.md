# Оформление покупки и заказа клиентом — полный процесс

Документ описывает: как клиент оформляет заказ/покупку, как это попадает в личный кабинет → «Операции», что отображается, и как устроена корзина.

---

## 1. Типы операций в приложении

В личном кабинете четыре типа операций (разные сущности в БД и разные экраны):

| Кнопка в профиле | Тип | Описание для клиента |
|------------------|-----|----------------------|
| 🛒 Заказы | `orders` | Я заказал товар «под заказ» у магазина |
| 🔒 Резервации | `reservations` | Я зарезервировал товар на 1–3 часа |
| 💰 Продажи | `purchases` | Я продал товар магазину (C2C: сдача товара) |
| 🛍️ Покупки | `sale-orders` | Я купил товар (магазин продал мне или C2C) |

Ниже разобраны **заказ** (orders) и **покупка через корзину / кнопку** (sale-orders и корзина).

---

## 2. Полный процесс: заказ товара «под заказ» (Order)

### 2.1 Откуда клиент попадает на оформление

- **Страница товара** или **карточка на витрине** — кнопка действия зависит от типа товара (см. `productActionType.js`). Для товара с типом «под заказ» (`is_made_to_order`) показывается действие **«Заказать»**.
- **Bottom Sheet корзины** (после добавления товара в корзину на странице избранного): при нажатии основной кнопки с текстом «Заказать» открывается страница оформления заказа.

Цепочка вызовов:

1. **Кнопка «Заказать» на странице товара / в модалке товара**  
   → вызывается `showOrderPage(productId, fromCart)` из `orders.js`.  
   `fromCart = false` → при закрытии страницы заказа возврат на страницу товара.

2. **Кнопка в Bottom Sheet (избранное)**  
   В `cartBottomSheet.js` при `actionType === 'order'`:
   - закрывается bottom sheet;
   - вызывается `showOrderPage(currentProduct.id, false)`.

Итого: и с витрины/страницы товара, и из корзины (bottom sheet) открывается **одна и та же страница оформления заказа** `#order-page`.

### 2.2 Страница оформления заказа (#order-page)

- **Файл:** `webapp/js/orders.js` — `showOrderPage(productId, fromCart)`, `setupOrderFormHandlers(productId)`, `submitOrder(productId)`.
- **Шаги (steps):** многошаговая форма (шаг 1 — количество и т.д., шаг 3 — отправка).
- **Данные формы:** количество, промокод, имя, фамилия, отчество, код страны телефона, телефон, email, примечание, способ доставки (доставка/самовывоз).
- **Валидация:** обязательны имя, фамилия, телефон; количество не больше доступного (с учётом резерваций).

При нажатии «Оформить заказ» (шаг 3):

1. Собирается объект `orderData` (product_id, quantity, контакты, delivery_method и т.д.).
2. Вызывается **createOrderAPI(orderData)** из `webapp/js/api/orders.js`.
3. Запрос: **POST** `${API_BASE}/api/orders/`, тело — JSON `orderData`, заголовки с `X-Telegram-Init-Data`.
4. После успешного ответа:
   - показ сообщения «Заказ оформлен! Статус: ожидание»;
   - закрытие страницы заказа (возврат на страницу товара или корзину);
   - обновление данных приложения, корзины и счётчиков операций (`updateActivityCounts`).

### 2.3 Бэкенд: создание заказа

- **Файл:** `backend/app/routers/orders.py` — эндпоинт **POST /api/orders/**.
- **Авторизация:** из заголовка `X-Telegram-Init-Data` через `validate_init_data_multi_bot` получается `ordered_by_user_id` (клиент).
- **Проверки:** товар существует; у товара `is_made_to_order = True`; клиент не владелец товара (`ordered_by_user_id != product.user_id`).
- **Действия:**
  1. Создаётся **snapshot** товара на момент операции: `create_product_snapshot(..., operation_type='order')` — сохраняются название, цены, описание, фото и т.д.
  2. Создаётся запись **Order**: product_id, snapshot_id, user_id (владелец магазина), ordered_by_user_id, quantity, контакты, delivery_method, status='pending', is_completed=False, is_cancelled=False, order_number (уникальный номер).
  3. Владельцу магазина при наличии бота отправляется уведомление в Telegram (товар, кто заказал, количество, контакты, кнопка «Посмотреть заказы»).

После этого заказ сразу попадает в «Мои заказы» клиента (см. раздел 4).

## 3. Покупка через корзину и кнопку «Купить» (Sale / C2C)

### 3.1 Два сценария покупки

- **Покупка одного товара (с витрины / из модалки / из bottom sheet):**  
  Для товара с типом «продажа» (`is_for_sale` и т.п.) кнопка действия — «Купить». В `cartBottomSheet.js` при `actionType === 'sale'` вызывается **showSaleOrderModal(currentProduct)** из `sale_orders.js` — открывается форма оформления **покупки** (sale order), один товар.
- **Корзина (страница cart-page-new):**  
  Товары добавляются в корзину (хранятся в `cartStore.js` + при необходимости синхронизация с сервером). На странице корзины есть кнопка **«К оформлению»** (`#cart-new-checkout-btn`). Сейчас она **не создаёт заказы/покупки**: в `cartNew.js` на ней висит заглушка `alert('Оформление заказа будет реализовано позже')`. То есть массовое оформление всей корзины через один клик пока не подключено к API.

Итого:  
- Один товар «Купить» → форма sale order → создаётся запись в sale_orders → попадает в «Покупки» в операциях.  
- Корзина «К оформлению» → пока только заглушка, заказы/покупки не создаются.

### 3.2 Bottom Sheet корзины (добавление в корзину и действие)

- При клике по кнопке корзины на карточке товар **сразу добавляется в корзину** с количеством 1, затем открывается bottom sheet.
- В bottom sheet можно менять количество (оно синхронизируется с корзиной).
- Текст основной кнопки и действие зависят от типа товара (`getProductActionType` в `productActionType.js`):
  - **order** → «Заказать» → `showOrderPage(product.id, false)` (страница заказа);
  - **sale** → «Купить» → `showSaleOrderModal(currentProduct)` (форма покупки);
  - **reserve** → «Резервировать» → форма резервации;
  - **purchase** → «Продать» → форма продажи (клиент продаёт магазину);
  - и т.д.

То есть оформление **заказа** (order) и оформление **покупки** (sale) — разные потоки и разные API (orders vs sale_orders).

## 4. Как заказ/покупка попадает в личный кабинет → «Операции»

### 4.1 Вход в операции

- Меню (☰) → «Личный кабинет» → страница **#profile-page**.
- Блок **«📦 Мои операции»**: четыре кнопки — Заказы, Резервации, Продажи, Покупки (`profile.js` вешает обработчики, например `profile-orders-btn` → `openOrdersPage()`).

### 4.2 Страница «🛒 Заказы» (orders)

- **Открытие:** `openOrdersPage()` в `operationsOrders.js` → показ страницы `#orders-page`, вызов `loadOrdersData()`.
- **Данные:**
  - Активные: **GET /api/orders/my** — заказы текущего пользователя (клиента), которые ещё не завершены и не отменены.
  - Завершённые: **GET /api/orders/history** — вся история заказов пользователя.
- В `loadOrdersData()` оба списка объединяются; на фронте разделяются на активные (`!is_completed && !is_cancelled`) и завершённые (`is_completed || is_cancelled`).
- **Отображение:** два блока — «Активные» и «Завершённые»; в каждом список карточек. Карточки создаёт **createOperationCard(item, 'orders', status)** из `operationsBase.js`.

### 4.3 Что показывается в списке (карточка операции)

Для заказов (и аналогично для продаж/покупок) в карточке отображается:

- Фото товара (из snapshot или плейсхолдер), 80×80.
- Название товара.
- Цена и количество (например «1 000 ₽ × 2 шт.»).
- Дата создания (📅).
- Бейдж статуса:
  - Активные: «⏳ В обработке»;
  - Завершённые: «✅ Выполнен» или «❌ Отменён».
- При недоступности товара — бейдж «⚠️ Товар недоступен».

Цвет полоски слева у карточки задаётся в CSS по `data-type` (для заказов — зелёный и т.д.). Карточка кликабельна → открывается страница детали операции.

### 4.4 Страница детали операции (#operation-detail-page)

- **Открытие:** клик по карточке в списке заказов/продаж/покупок → **openOperationDetailPage(type, item)** в `operationsDetail.js` (type = 'orders' | 'purchases' | 'sale-orders').
- **Заполнение:** **renderOperationDetail(type, item)** — все данные из переданного `item` (с бэкенда приходят объекты с вложенным `product` из snapshot).

Отображается:

1. **Номер заказа** — если есть `item.order_number`; по клику копируется в буфер.
2. **Статус и дата** — одна строка: дата создания и бейдж (В обработке / Выполнен / Отменён).
3. **Карточка товара** — мини-карточка из snapshot: фото, название, цена (как на карточке товара, read-only). При наличии товара можно открыть модалку товара.
4. **Детали заказа/покупки:**
   - Для заказа (orders): количество, цена за ед., сумма, скидка, итого к оплате, экономия (если есть), способ доставки.
   - Для продажи (purchases) и покупки (sale-orders): аналогичные поля плюс способ оплаты и т.д.
5. **Контактная информация:** ФИО, телефон, email, адрес (если есть).

Кнопка «Назад» возвращает на список соответствующего типа операций (заказы / продажи / покупки).

## 5. Сводная схема потоков

```
[Витрина / Страница товара / Избранное]
        │
        ├─ Товар «под заказ» → Кнопка «Заказать» (или из Bottom Sheet)
        │       → showOrderPage(productId)
        │       → Форма #order-page (шаги 1–3)
        │       → submitOrder() → createOrderAPI(orderData)
        │       → POST /api/orders/
        │       → Бэкенд: snapshot + Order, уведомление владельцу
        │       → Заказ появляется в «Мои заказы» (GET /api/orders/my и history)
        │
        ├─ Товар «на продажу» → Кнопка «Купить» (или из Bottom Sheet)
        │       → showSaleOrderModal(product)
        │       → Форма sale order → API sale_orders
        │       → Запись появляется в «Покупки» (sale-orders)
        │
        └─ Корзина (страница cart-page-new)
                → Кнопка «К оформлению» → пока заглушка (оформление не реализовано)

[Личный кабинет] → «Мои операции»
        │
        ├─ 🛒 Заказы → #orders-page
        │       → getMyOrdersAPI() + getOrdersHistoryAPI()
        │       → Список карточек (createOperationCard)
        │       → Клик по карточке → #operation-detail-page (детали заказа)
        │
        ├─ 🔒 Резервации → отдельная страница и API
        ├─ 💰 Продажи → purchases (мои продажи)
        └─ 🛍️ Покупки → sale-orders (мои покупки)
```

## 7. Итог

- **Заказ (order):** один товар «под заказ» → страница заказа → POST /api/orders/ → snapshot + Order → сразу попадает в «🛒 Заказы» в операциях. В списке — карточки (фото, название, цена, количество, дата, статус); по клику — деталь (номер, статус, товар по snapshot, итого, контакты).
- **Покупка (sale-order):** один товар «на продажу» → форма покупки → API sale_orders → попадает в «🛍️ Покупки» в операциях; отображение аналогично (список + деталь).
- **Корзина:** товары хранятся в корзине; кнопка «К оформлению» создаёт **сделку (Deal)** через API deals (checkout/start → checkout/confirm). Оформление по одному товару идёт через «Заказать» или «Купить» в bottom sheet / на странице товара.

Если нужно, можно отдельно расписать только бэкенд (модели Order, snapshot, эндпоинты) или только вёрстку/стили страниц операций.

## 8. Расчёт суммы оплаты и формы оплаты — полная картина

Ниже описано, как считаются цены, как учитывается способ оплаты (карта / наличные и др.) при оформлении и как это отображается в сделке в личном кабинете.

### 8.1 Модель цен на товар (одна точка правды)

- **Файл:** `webapp/js/utils/priceUtils.js`.
- **Базовая цена:** `getBasePrice(product)` — приоритет `price_card` > `price`.
- **По карте:** `getFinalCardPrice(product)` — базовая цена с учётом скидки (`discount`).
- **Наличными:** `getFinalCashPrice(product)` — если задан `price_cash`, используется он (и при скидке — согласованная логика с картой); иначе `null`.
- **Единый расчёт для UI и итогов:**  
  `getEffectiveUnitPrice(product, paymentMethod)` — возвращает цену за единицу в зависимости от способа оплаты:  
  - если способ «наличные» (`normalizePaymentMethod(paymentMethod) === 'cash'`) и есть `price_cash` → используется цена наличными;  
  - иначе используется цена по карте (или fallback для is_for_sale: price_fixed / price_from / price_to).
- **Нормализация способа оплаты:** `normalizePaymentMethod(pm)` — наличные приводятся к `'cash'`, всё остальное (карта, онлайн и т.д.) к `null` (по карте). Остальные значения (transfer, other) в расчёте цены не меняют итог — только отображаются как подпись.

Итого: **на сумму влияет только выбор «наличные» vs «по карте»** (через наличие/использование `price_cash`).

### 8.2 Корзина (страница cart-page-new)

- **Итог по выбранному способу оплаты:**  
  `getSelectedCartTotal(promoCode, paymentMethod)` из `cartStore.js` — сумма по выбранным позициям: для каждой позиции берётся `getEffectiveUnitPrice(item.product, paymentMethod)` × количество. Промокод в коде не применяется (TODO).
- **Выбор способа оплаты:** в блоке итогов две строки: «По карте» и «Наличными» (классы `cart-payment-choice`, `data-payment="card"` / `data-payment="cash"`). При клике вызывается `setCartPaymentMethod('cash' | null)` и `updateCartSummary()`. Итог в футере и в блоке сводки пересчитывается под выбранный способ.
- **Файлы:** `webapp/js/cart/cartNew.js` (обработчики, `updateCartSummary`), `webapp/js/cart/cartStore.js` (`getSelectedCartTotal`, `getEffectiveUnitPrice` из `priceUtils.js`).

То есть **в корзине сумма отображается с учётом формы оплаты** (карта / наличные).

### 8.3 Оформление покупки одним товаром (Sale Order — кнопка «Купить»)

- **Форма:** страница/модалка из `sale_orders.js` (шаги: количество → контакты → доставка и оплата).
- **Способ оплаты в форме:** в шаге 3 есть радио-кнопки `sale-order-page-payment-method`: online, crypto, cash. Выбранное значение уходит на бэкенд как `payment_method` и сохраняется в `SaleOrder`.
- **Расчёт «Итого» в форме:** в `updateSaleOrderTotal()` используется **не** `getEffectiveUnitPrice`, а локальная функция `getProductNumericPrice(product)` — она берёт цену по карте (price/price_fixed/price_from + скидка) и **не зависит от выбранного способа оплаты**. То есть в момент оформления в форме сумма не пересчитывается при переключении онлайн/крипто/наличные.
- **На бэкенде:** `backend/app/routers/sale_orders.py` при создании sale order сохраняет `payment_method`, но **не пересчитывает** цену по способу оплаты. Snapshot хранит `price_card`, `price_cash` и т.д.; в ответах отдаётся product из snapshot.
- **В личном кабинете (деталь операции):** в `operationsDetail.js` для типа `sale-orders` используется `getEffectiveUnitPrice(product, paymentMethod)` и `paymentMethod` берётся из `item.payment_method`. Поэтому **в детали покупки в ЛК** «Цена за ед.» и «Итого к оплате» показываются уже **с учётом способа оплаты** (карта vs наличные). Способ оплаты отображается отдельной строкой («Способ оплаты»).

Итого: при оформлении одного товара форма оплаты **учитывается только при отображении в ЛК**; в самой форме оформления сумма не пересчитывается при смене способа оплаты.

### 8.4 Сделка из корзины (Deal)

- **Старт оформления:** «К оформлению» в корзине → `startDealCheckoutAPI({ items })` → **POST /api/deals/checkout/start**. В теле только список позиций `{ product_id, quantity }`; способ оплаты на этапе start **не передаётся**.
- **Расчёт суммы на бэкенде:** в `backend/app/routers/deals.py` функция `_create_draft_deal` для каждой позиции вызывает `_get_unit_price_for_sale(product)`. В `_get_unit_price_for_sale` используется только `price_card` или `price`, скидка; **price_cash не используется**. То есть сумма сделки при создании черновика всегда считается «по карте». Затем для каждой позиции считаются `price_per_unit`, `line_total`, `total_amount` по сделке и сохраняются в БД.
- **Подтверждение:** **POST /api/deals/checkout/confirm** — в теле приходят `payment_method`, `delivery_method`, контакты, адрес, комментарий. Бэкенд только сохраняет `payment_method` в сделке; **пересчёта total_amount и цен позиций по способу оплаты нет**. Сумма в сделке остаётся той, что посчитана при start (по карте).
- **Отображение в ЛК (деталь сделки):** в `operationsDetail.js` для типа `deals` выводятся `deal.total_items_count`, `deal.total_amount` (из API), а также подпись «Оплата: Картой / Наличными / …» из `deal.payment_method`. То есть в сделке в ЛК показывается **одна и та же сумма** независимо от выбранного способа оплаты; способ оплаты влияет только на подпись.

Итого: при оформлении сделки из корзины **форма оплаты не влияет на расчёт суммы**: сумма фиксируется при checkout/start по «карточной» цене; при confirm способ оплаты только сохраняется и отображается в ЛК.

### 8.5 Деталь операции в ЛК — сводка по типам

| Тип операции   | Откуда берётся сумма | Учёт способа оплаты |
|----------------|----------------------|----------------------|
| orders         | Snapshot; unitPrice = getEffectiveUnitPrice(product, paymentMethod), subtotal = unitPrice × qty | Да: в детали показывается цена и итог по выбранному способу (карта/наличные). |
| purchases      | Аналогично: getEffectiveUnitPrice(product, paymentMethod) | Да. |
| sale-orders    | Аналогично: getEffectiveUnitPrice(product, paymentMethod) | Да: в детали — да; в форме оформления одного товара при вводе — нет. |
| deals          | deal.total_amount и по позициям price_per_unit, line_total с бэкенда | Нет: сумма зафиксирована при start (по карте); payment_method только подпись. |
